# Sesi 11 — Ganti pembayaran ke Lynk.id, Midtrans dinonaktifkan

**Tanggal:** 29 September 2026
**Konteks:** User ingin memakai **Lynk.id** sebagai metode pembayaran langganan,
"karena di halaman integrasi Lynk.id hanya ada integrasi webhook". Menyusul:
"nonaktifkan sementara integrasi Midtrans".

---

## Keputusan

- **Webhook saja sudah cukup.** Pola payment-link + webhook memang lengkap untuk
  langganan: pelanggan bayar di halaman Lynk.id, Lynk.id memanggil webhook kita
  saat sukses, kita aktifkan langganan. Tidak butuh API pembuatan invoice.
- **Midtrans dinonaktifkan, BUKAN dihapus.** Sakelar env `PAYMENT_PROVIDER`
  (default `lynkid`). Balik lagi cukup set `PAYMENT_PROVIDER=midtrans` — nol baris
  kode diubah. Ini memenuhi "nonaktifkan sementara" tanpa kehilangan pekerjaan
  Midtrans yang sudah teruji.

## Yang dibangun

**Sakelar penyedia pembayaran** (`lib/config.ts`)
`paymentProvider()` + `hasLynkid()`. `hasMidtrans()` di `lib/billing/midtrans.ts`
kini mengembalikan `false` kecuali provider = `midtrans`, jadi seluruh rute
Midtrans (create / notification / reconcile) otomatis membalas 503 tanpa disentuh.
UI membaca `NEXT_PUBLIC_PAYMENT_PROVIDER`.

**Aktivasi tetap satu pintu** (`lib/billing/activate.ts`)
Direfactor jadi inti provider-agnostic `terapkanKeadaanPembayaran()`. Midtrans
(`terapkanStatusPembayaran`, kini pembungkus tipis) dan Lynk.id memakai inti yang
SAMA. Ini menjaga aturan lama: perhitungan masa aktif hanya ada di satu tempat,
jadi dua penyedia tidak mungkin menyimpang. Saat lunas: `subscription → "active"`,
`currentPeriodEnd = max(sisa masa aktif, now) + 30 hari` — hari yang sudah dibayar
tidak hangus.

**Provider Lynk.id** (`lib/billing/lynkid.ts`) — sesuai dokumentasi resmi Lynk.id:
- **Verifikasi `X-Lynk-Signature`**: `SHA256(grandTotal + refId + message_id + merchantKey)`,
  dibandingkan dengan `timingSafeEqual`. `LYNKID_WEBHOOK_SECRET` menyimpan
  **merchant key** (muncul di dashboard Lynk.id setelah URL webhook disimpan).
- **Baca payload** event `payment.received`: status `data.message_action="SUCCESS"`,
  email `data.message_data.customer.email`, id transaksi `refId` (kunci idempotensi),
  produk `items[].title`.
- **Deteksi paket pakai `totals.totalPrice`, BUKAN `grandTotal`** — lihat jebakan
  di bawah.
- **Email dari pertanyaan tambahan** `items[].questions` (JSON string) ikut dibaca,
  diprioritaskan bila pembeli mengisi "Email akun Zavi".

**Webhook** `app/api/payment/lynkid/route.ts` — verifikasi tanda tangan →
cocokkan ke tenant (via email → pembayaran pending terakhir, atau tebak paket) →
serahkan ke inti aktivasi. Idempoten (kunci `LYNKID-<refId>`).

**Create** `app/api/payment/lynkid/create/route.ts` — catat pembayaran pending +
kembalikan link checkout Lynk.id untuk paket. Butuh `LYNKID_LINK_BASIC`/`_PRO`.

**Store** — `PlatformStore.getTenantByEmail()` (Firestore + memory), untuk
mencocokkan pembeli ke akun saat webhook tidak membawa referensi order kita.

**Halaman langganan** (`app/langganan/page.tsx`) — otomatis beralih ke alur
Lynk.id saat provider = lynkid: buka link checkout di tab baru, lalu tunggu
konfirmasi webhook. Alur Midtrans tetap ada untuk saat dihidupkan lagi.

**Konfigurasi** — `.env.example`, `.env.local`, dan `apphosting.yaml` ditambah
`PAYMENT_PROVIDER`, `NEXT_PUBLIC_PAYMENT_PROVIDER`, `LYNKID_WEBHOOK_SECRET`
(secret), `LYNKID_LINK_BASIC/PRO`.

## Cara mengaitkan pembayaran ke akun

Lynk.id tidak punya field "external_id" yang kita titipkan, jadi pengaitan
bertumpu pada **email**:
1. Termudah — pelanggan bayar pakai email yang sama dengan email login Zavi.
2. Paling andal — tambahkan pertanyaan "Email akun Zavi" di produk Lynk.id;
   jawabannya otomatis dibaca webhook dan diutamakan.

Deteksi paket: namai produk mengandung "basic"/"pro", atau samakan harganya
dengan harga paket (Basic 99.000 / Pro 249.000).

## Jebakan yang ditemukan: `grandTotal` vs `totalPrice`

Di payload Lynk.id, `totals.grandTotal` adalah **jumlah bersih yang diterima
penjual setelah dipotong biaya layanan** (contoh dokumen: totalPrice 25.000 →
grandTotal 22.000 setelah convenienceFee). Mencocokkan paket dengan `grandTotal`
pasti meleset. Yang cocok dengan harga paket adalah `totals.totalPrice` (harga
produk kotor). Tetapi **tanda tangan tetap pakai `grandTotal`**, sesuai rumus
Lynk.id — dua nilai untuk dua tujuan berbeda, jangan tertukar.

## Verifikasi

Dev server sempat *segfault* (lihat jebakan lingkungan), jadi verifikasi lewat
build + unit test yang lebih andal:

| Uji | Hasil |
|---|---|
| Build produksi (TypeScript) | **exit 0**, lolos tanpa error ✅ |
| 11 unit test algoritma (parsing + signature) | **11/11 lulus** ✅ |
| Signature VALID (huruf besar/kecil) | diterima ✅ |
| Signature SALAH / tanpa signature | ditolak (403) ✅ |
| `grossIdr` = totalPrice, bukan grandTotal | benar ✅ |
| email pembeli & email dari pertanyaan | terbaca ✅ |
| Midtrans `POST /api/payment/create` | **503 dinonaktifkan** ✅ |

Uji signature memakai payload contoh dari dokumentasi Lynk.id; rumus dibandingkan
langsung dengan kode contoh Lynk.id (`amount + ref_id + message_id + secretKey`).

## Yang harus user lakukan (go-live Lynk.id)

1. Buat 2 produk/link checkout di Lynk.id (Basic & Pro) → isi `LYNKID_LINK_BASIC`
   dan `LYNKID_LINK_PRO`.
2. Daftarkan URL webhook **tanpa query** di Lynk.id → Integrasi → Webhook:
   `https://<domain>/api/payment/lynkid`
3. Salin **merchant key** yang muncul → `LYNKID_WEBHOOK_SECRET` (lokal di
   `.env.local`; produksi: `firebase apphosting:secrets:set LYNKID_WEBHOOK_SECRET`).
4. (Opsional) tambahkan pertanyaan "Email akun Zavi" di produk Lynk.id.

## Masih terbuka

1. **Keputusan UI**: apakah menambahkan instruksi "isi Email akun Zavi" di halaman
   langganan supaya pelanggan tahu harus mengisinya saat checkout — atau cukup
   andalkan email yang sama. **Menunggu jawaban user.**
2. **Beli kredit AI lewat Lynk.id belum ada** — tombolnya dimatikan sementara
   saat provider = lynkid (dulu lewat Midtrans). Perlu produk Lynk.id sendiri
   kalau mau dihidupkan.
3. Seluruh kerja masih belum di-commit.

## Jebakan lingkungan: dev server Turbopack segfault

`npm run dev` beberapa kali mati mendadak (**exit 139 / segfault**) tepat saat
request pertama memicu kompilasi rute on-demand. Bukan dari kode — crash terjadi
di runtime Node/Turbopack, bukan sebagai exception JS. Karena itu verifikasi
dialihkan ke **build produksi + unit test**, yang tidak bergantung pada dev
server. Untuk menjalankan lokal, `npm run dev` biasanya tetap bisa; kalau crash,
ulangi atau pakai `npm run build && npm start`.
